# Coref-critical relabelling and query-term injection audit

Generated by `analysis/relabel_critical.py`. Reads only the committed JSON in
`test-*/test-*-data/`; no notebook, model, or retrieval run is involved.

## Method

For every question flagged `coref_critical: true` in tests 4-7:

1. Concatenate the question's gold chunk(s), once from `original_chunks.json` and once
   from `coref_chunks.json`.
2. Tokenise both into lowercased content words, dropping a fixed English stopword list and
   every token of length <= 2.
3. `added = coref_tokens - original_tokens`.
4. `critical_confirmed` if `added` is non-empty (the rewrite genuinely introduced entity
   information the original gold chunk lacked); `critical_unsupported` if `added` is empty.
5. `injection` if `added` intersects the question's own content-word tokens — the rewrite
   inserted into the gold chunk a term the query is searching for.

### Two tokenisers, because the choice changes the answer

| tokeniser | pattern | `F-1` becomes |
| --- | --- | --- |
| `hyphenated` (**primary**) | `[a-z0-9]+(?:-[a-z0-9]+)*` | `f-1` (kept) |
| `strict` (sensitivity check) | `[a-z0-9]+` | `f` + `1` (both dropped, length <= 2) |

A second axis: `added` is computed over the **union** of a question's gold chunks. For a
question with more than one gold chunk, a term the rewrite added to chunk A may already be
present in chunk B, so the union hides it. The `per_chunk` variant takes the union of the
per-chunk differences instead. Both are reported.

The hyphen-aware rule is primary. Under `strict`, test-4 q15 (*"These engines"* ->
*"The F-1 engines"*) and q16 (*"It provided thrust"* -> *"The S-II provided thrust"*)
are counted as adding nothing, even though the rewrite plainly introduced a new entity
string that the query names. That is a tokenisation artefact, not a finding. Both counts
are reported below so the difference is visible; they differ only on test-4.

**Important scope limit:** every Recall@5 / R@5_crit number reported in the
`test-*-findings.md` files and in the README was computed against the **original**
`coref_critical` labels. Nothing here re-runs retrieval, so no per-test "critical" metric
has been recomputed against the `critical_confirmed` labels. Treat the counts below as an
audit of the label set, not as corrected metrics. Recomputing the critical-subset metrics
would require re-running the notebooks.

`critical_unsupported` = the coref rewrite of the gold chunk(s) adds **no new content word**
at all, so the entity the question names was already present in the original chunk. Coref
cannot have helped retrieval on those questions by the mechanism the hypothesis proposes.

`query-term injection` = the tokens the rewrite added to the gold chunk overlap the
question's own content words. On these questions any recall gain is partly mechanical:
the rewrite put the query's search term into the indexed text.

## Caveats on this audit itself

- The stopword list and the length-2 cutoff are heuristics. The test-4 q15 / q16 cases show
  the cutoff is not neutral: it decides whether a short entity string counts as added
  information. Both tokenisations are reported for that reason.
- `added` is a set difference over the union of a question's gold chunks, so for a
  multi-gold question a term added to one chunk can be masked by its presence in another.
  The `per_chunk` column in the sensitivity table shows the effect; it changes only test-4
  (q2, q3, q13), all three of which have two gold chunks.
- Injection is measured as token overlap, not as evidence of intent. A rewrite that resolves
  a pronoun to the entity a natural question would also name will register as injection; the
  point is that on those questions the recall gain cannot be separated from the term match.
- `critical_unsupported` does not mean the question is bad, only that coref cannot explain
  any retrieval change on it. The rewrite may still have altered the embedding.
- No retrieval metric in this repo has been recomputed. See the scope limit above.
